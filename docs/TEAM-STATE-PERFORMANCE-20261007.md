# 团队状态读取优化（2026-10-07）

## 已实现：不改变持久格式的两层加速

- `readTeam` 与 `readTeamSync` 对同一团队、完全相同的文件字节缓存完整校验结果。每次仍重新解析成独立对象并执行成员权限范围归一化；不同字节、不同 team ID、进程重启均重新完整校验。只缓存成功结果，最多 32 个摘要。
- 活动总览使用 `readTeamActivity`，仅投影队伍、成员和任务字段。首次读取仍完整验证；后续若文件的设备号、inode、大小、纳秒级 mtime/ctime 均未变，仅返回轻量投影的独立副本。该路径只用于只读展示；授权、调度、审核、写入继续使用完整记录。
- `team.json` 格式和所有历史证据保持原样。旧团队无需迁移，已有脚本仍可读取。

## 定向测量与回归

在同一台生产宿主机上，以独立 Node 进程只读打开两份真实团队记录；数值受同时运行的 Web 负载影响，仅用于看同一进程内冷、热路径差异：

| 团队记录 | 文件大小 | 完整读取首次 / 再次 | 活动总览首次 / 再次 |
|---|---:|---:|---:|
| V4 上海租赁试跑 | 9.56 MiB | 1871 / 185 / 169 ms | 1801 / 4 / 2 / 1 ms |
| V3 上海与一线研究 | 8.13 MiB | 928 / 139 / 98 ms | 684 / 1 / 1 / 1 ms |

回归覆盖：对象不共享、改写后重新验证、无效依赖拒绝、不同 team ID 不复用结果、活动总览与完整记录输出一致、历史质量记录仍可完整读取。`tsc -p tsconfig.json` 和 26 个状态/调度定向测试通过。

## 下一阶段：真正的持久冷热拆分

`qualityRuns` 历史在 V4 记录中约占 7 MiB。若要使调度和审核的完整读取也免于解析这些历史，需先更新所有直接读取 `team.json` 的路径（含报告交付、诊断、维修提示及维护脚本），并为同步冷恢复读提供相同的历史加载能力。安全的提交顺序应是：先写不可变、带 SHA-256 的历史文件；校验落盘；最后原子提交含引用的主记录。读取时验证引用摘要，旧版单文件记录继续可读。迁移要经过崩溃点、归档/恢复和并发写回归后才能开启。

当前代码只完成兼容的内存冷热分离；**没有迁移现有团队记录，也没有重启生产 `dsh-web`**。生产插件目录是源码仓库的符号链接，仓库同时含有大量其他未提交改动；任何重启都会加载整包的当前编译结果，应先隔离发布内容并核验在途任务。
