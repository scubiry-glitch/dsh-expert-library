# 专家协作室 v0.9 评审：面向客户自助使用的修订建议

日期：2026-10-08  
评审对象：[统一账号、新建研究会话与用量管理 v0.9](ACCOUNT-AND-NEW-SESSION-PRD-20261008.md)  
目标：不同客户登录独立页面后，自己完成**对话 → 查询 → 生成报告 → 找回与下载**，管理员能管理账号和用量。

## 结论

v0.9 已覆盖联合登录、会话归属、三类 `@`、数据 tab、用量统计和单实例多工作区的技术边界。最大缺口是**客户交付闭环**：文档详细写了“生成计划、启动团队”，但“客户如何选择报告、看到成稿、下载、修订”仍散落在现有审阅能力中。另一项必须先处理的是新客户的隔离和报告发布权限。建议先把产品主流程写清，再把已有接口和新增接口接上。

## 建议改动，按优先级排序

| 优先级 | v0.9 的缺口 | 建议补入下一版的决定 | 验收点 |
|---|---|---|---|
| P0 | “账号”同时承担登录人、客户归属和工作区边界 | 增加稳定的 `account_id`（客户/计量/工作区归属）与 `user_id`（登录人）；`account_memberships` 管角色。首批即使一个客户只有一位用户，也建立一人一账号的成员关系 | 两个客户绝不共享会话、数据、报告或用量；同一客户追加成员时无需迁移会话所有权 |
| P0 | 当前入口仍是分享码审阅页，不是新客户登录首页 | 明确 `/login`、`/app` 与旧分享入口的职责；首次有效登录幂等创建/加入客户账号与工作区，直接落到“我的会话”。新建后验证空白 captain 确实能调用智见小秘书、查询和报告工具 | 新客户无旧链接、无需管理员手工建 captain，也能在 3 分钟内发出第一问 |
| P0 | 生成计划后缺少客户视角的报告交付流程 | 工作区加入明确的“生成报告”路径：选报告类型/模板和交付格式 → 核对议题、数据、专家、预算 → 确认启动 → 查看状态/待确认 → 成稿预览、下载、版本、修订与失败重试。保留现有质量与人工门 | 客户从空白会话完成一份可下载的 HTML/PDF 报告，断线后仍能回到当前进度 |
| P0 | 现有“分享链接”可发布匿名可访问的静态文件 | 新客户报告默认仅账号成员可读；分享改为明确操作，限定对象/能力/期限并可撤销。旧审阅分享单独兼容，不能自动用于新账号报告 | 未授权的 URL、原始 Host API、文件路径和静态渲染路径都不能读到别人的报告 |
| P0 | 用量展示有了，客户无限查询/跑团队的成本边界未成型 | 加每账号及每会话的 token/并发/查询额度和管理员停用开关；启动前展示预算上限，预留单次请求可能超额的余量，达到上限后暂停新调用并明确续跑方式。数据源 API 费用独立于 token 计量 | 两账号同时跑研究时互不挤占授权额度；达到上限后不再启动新的模型/数据请求 |
| P1 | 数据源、领域包、专家“可用”尚未绑定客户可用套餐/许可 | 账号建立时加载可用能力清单；`@` 菜单、模型、模板和报告路径按账号权益过滤。`@智见` 的真实目录 ID 与底层来源需在上线前注册和核验 | 客户只看到可用对象；没有许可时给出明确提示，不返回编造数据 |
| P1 | 管理员只有用量页，客户开通与停用仍缺操作面 | 给管理员增加账号清单、状态、成员、权益、额度和审计；用量页可下钻，但不能代替账号管理 | 可开通、暂停、恢复一个客户账号，且变更即时影响登录、查询、团队和报告访问 |
| P2 | 历史会话、所有第三方登录与复杂协作并列推进 | 保留完整目标，但先以少量新客户、一个已验证身份源、一个可验证数据通道和一个报告模板做端到端试点；随后接入其余身份源/模板并分批迁移历史 | 试点期间旧分享页继续可用；扩大范围前完成跨账号隔离和完整交付演练 |

## 建议写进 PRD 首页的客户主流程

1. 客户打开独立登录页，使用已开通的智号或开发者中心身份进入；首次进入自动获得自己的账号工作区和可用能力。
2. 点击“新建会话”，在**会话** tab 与智见小秘书讨论问题；输入 `@` 可选数据源、领域包或专家。
3. 查询到的表格自动进入**数据** tab；客户先看结果清单、点击再看表格，决定哪些结果作为报告材料。
4. 点击“生成报告”，在**工作区**选择报告模板和交付范围，核对数据、专家、预算与计划后确认启动。
5. 页面显示真实进度、待确认事项和失败原因；成稿后在工作区“研究成果”预览、下载 HTML/PDF，必要时发起新版本修订。
6. 客户随时从“我的会话”找回对话、数据、报告和 token 用量；管理员从独立界面看账号、额度和消耗。

这个流程应成为首版验收的主线。每一个客户可见按钮都需要对应状态、权限和失败恢复；后台阶段名可以保留，但页面文案应围绕“提问、查询、生成报告、查看报告”。

## 当前代码与 v0.9 的关键落差

- `assets/review/index.fast.html` 的未登录状态仍是“分享码 / 免密链接”，侧栏也要求粘贴授权链接；因此登录首页、我的会话和新建会话都需要新入口，不能只改按钮文字。
- `src/host/review-routes.ts` 的 `/api/issue` 依赖既有 plan/team，当前空白 captain 不能直接走这套审阅授权与消息入口。须做一条真实的新客户链路验证：首次登录 → 工作区供给 → 空白 session → 首条消息 → 查询 → 计划 → 报告。
- 现有工作区已有“研究成果”、文档阅读与下载；`src/report-bundle.ts` 也定义报告的 MD/HTML/PDF 产物要求。下一版应把这些能力写成客户能理解的“报告状态、成稿、版本、下载和修订”流程，而不是再造报告引擎。
- 当前 `src/host/review-routes.ts` 的 `/api/document-share` 调用 `src/host/review-publication.ts`，把文件写到匿名可访问的 `/render/expert-library/...` 静态路径。新客户报告必须走默认私有的读取与受控分享流程；现有行为仅作为旧审阅分享兼容，并核验实际部署是否开放该路径。
- v0.9 的每 `user_id` 一个 `workspace_id` 将登录人、客户和资源所有权绑定死。若“一个客户下多位员工”有可能，宜在落库前改为 `account_id → workspace_id`、`account_id ↔ user_id` 成员关系；个人客户只是一个成员的特例。
- DSH 本地源码有 token 用量投影，但还需核查**当前运行版本**能否稳定提供主会话、专家子会话和重试的原始用量；缺口必须展示为“部分统计”，不可直接用于扣费。

## 建议的交付门槛

**试点可用**：一位新客户用独立登录页进入，不靠分享码创建会话，能对话、查询、完成一个报告模板，查看/下载私有成稿；换设备可找回；管理员能看到该账号用量并设置上限。

**对外开放**：两位互不信任客户交叉测试登录、原始 Host API、SSE、文件、数据源、专家工具、报告静态路径、用量和额度均隔离；异常断线、取消、配额耗尽与失败重试可恢复。若单 DSH 实例无法证明文件/工具执行隔离，应在对外开放前改为账号级进程/容器隔离。

**后续扩展**：其他第三方登录、多人协作、更多领域包/数据源/专家、历史会话认领。它们保留在总需求内，以独立验收批次接入，不阻塞新客户闭环试点。

## 需要业务方最终确认的三项

1. “客户账号”是每个自然人独立，还是一家客户机构下可以有多位员工？建议数据结构先支持后者，首批用单成员账号。
2. 首批报告面向哪类客户和议题？建议指定一个已有质量门与数据通道的模板，规定 HTML/PDF 成稿及最长等待时间。
3. 客户能否把报告发给账号外的人？建议默认私有，外发时才创建有期限、可撤销的分享授权。
