## 一 目标与完成边界

用户应能在正式业务执行前，看懂并修改报告章节大纲、分析要求、所用工艺及参与者模型，确认具体版本后再执行。团队应自主完成研究、写作、渲染、独立审核和交付，避免无依据接管、参数猜测及不必要的等待消耗模型额度。

最终完成必须同时满足：本需求的功能和边界测试通过；真实租户可见的人工确认流程通过；全新业务会话从原始需求自主产出最终 MD、HTML、PDF 与必要附件；对同一批最终文件完成独立内容、来源、算术、视觉及三格式一致性验收。生成文件、计划已应用、材料已下发或内部状态 completed，单独均不足以判定完成。

保留领域包多 skill 发现与选择能力。AI 根据任务选择并解释，系统冻结选择、交付完整材料并核验结果；不得将所有报告硬编码成一个模板，也不得通过放宽检查器解决失败。

## 三 功能需求

### R1 根据实际进展管理接管与交接

系统应区分执行中、等待依赖、等待审核、等待模型容量、外部阻断及无进展状态。判断超时须读取当前任务版本、原生活跃状态、最近有效执行进展、产物发布和审核状态。单纯重复心跳或 status 调用不能无限延长任务。

模型不得仅凭主观“耗时过久”覆盖活跃任务。近期有效产出、已完成提交等待审核或明确排队时，应走对应等待或审核路径。必要接管必须原子校验当前所有者与任务版本，并记录原因和当时证据；租约、宽限期和可配置阈值需明确，不能用一个任意超时覆盖所有状态。

接管后保留旧版本历史。可复用产物须显式验证其 SHA、输入及适用范围，再记录新版本引用；不能静默转移旧审核结果，也不能要求模型为取得新所有权盲目重复发布相同文件。并发接管只能产生一个有效新版本。

### R2 由系统提供准确的提交与审核动作

每个角色获取当前可执行动作时，应同时得到正确的任务标识、版本、产物位置、缺失项和下一步。会话身份、所有权、审核人身份及内部关联标识由运行时确定，避免模型拼装内部状态。

作者完成提交前，由系统检查必需产物与当前版本，返回可一次修正的缺项清单。独立审核员获取完整审核材料及对应产物，审核结果绑定该版本。队长不得代理独立审核，作者不得自审；正常研究任务与报告工艺任务使用清晰、互不混淆的参数契约。

重复提交和网络结果不明时应先读回核对，不能制造重复发布、重复审核或重复推进。等待以事件和状态变化为依据，减少无状态变化的轮询和消息往返。状态页应显示真实外部阻断，不把额度耗尽伪装成持续处理中。

### R3 校验依赖是否必要以及产物顺序是否可执行

计划应声明任务所需输入及其来源，只有真实数据依赖才能阻止下游启动。可独立开展的研究或报告结构准备可提前进行；确需完整上游证据的结论必须等待，不能以提升并发为由使用未审核输入。

除任务 DAG 无环检查外，还应检查产物与验收条件的依赖。例如，报告完成要求证据台账，而台账任务依赖报告完成，会形成任务图表面无环、实际不可完成的顺序。暂存或批准前必须拒绝这类计划，或要求明确调整任务与交付归属。

当前 `t1 → (t2,t3) → t4 → t5 → t6` 只作为诊断案例，不应硬编码针对车公庄业务的特例。Kimi 请求并发保持已有约束，先减少无效轮次；未经容量证据验证不提高并发。

### R4 完整参考工艺并验证使用结果

所有进入正式报告工作流的入口，包括预置方案、AI 自编排和直接建队，必须声明最终报告交付及所选工艺。入口不能通过省略 reportBundle 或更换工具规避已生效的报告要求。普通非报告任务保持原有语义，不能机械套用报告工艺。

计划显示所选 skill、版本、样式及选择理由，并冻结域包与材料摘要。作者、渲染者、独立审核员分别获得适用的完整必读正文及参考件，保留与任务、会话、版本绑定的下发证据。上下文压缩或重启后仍应恢复这些约束；材料缺失、超限或版本漂移要明确阻断，不能静默截断。

区分材料送达、机器预检通过、独立内容审核通过三种事实。最终审核应检查章节展开、五件套内容、来源粒度、政策条件、计算及视觉，不能只验证收据存在或关键词命中。历史参考报告中的数据不得成为新业务事实依据。

### R5 结构化报告大纲与模型统一确认

在执行前提供默认展开、易读的计划卡，至少包括：业务目标与范围、报告章节大纲、每章核心问题及所需证据、交付格式与附件、所选工艺、任务依赖及验收要求、队长与成员及独立审核员的模型配置。

报告大纲必须是独立的结构化数据，支持增删、调整顺序和编辑分析要求，并映射到任务和交付要求；不能只把一段章节描述藏在任务文本里。模型配置支持逐角色选择 provider/model，展示推理强度、继承来源和可用性。修改本计划不应无提示地改变租户全局默认或历史会话。队长当前用于规划的模型与正式执行模型应区分清楚；不支持安全切换时须说明并在执行前通过受控方式完成，不能只改展示值。

用户点击“确认并开始执行”时，批准具体版本的大纲、模型、工艺、任务与验收条件。内容变更生成新版本，旧批准不能启动新版本。模型实际请求须与批准值一致；模型不可用时说明原因并要求修改计划，不能静默降级或切换。

确认前允许理解需求、读取用户已提供材料、发现工具与 skill、检查模型可用性及生成计划。这些规划动作可以使用模型。正式业务执行包括新业务数据检索、分析计算、研究成员启动和报告生产，须受批准门控；不能通过队长自己调用通用 shell 或 provider 工具绕过。实现时明确受控工具与执行路径，并用实际 Host 测试证明边界，不能只增加提示词或声称拦截所有任意代码。

### R6 人工确认与委托自动执行分别记录

默认走人工确认。待确认时保存计划、结束当前业务回合并正确处理系统持有的 Goal 等待状态；用户确认后恢复匹配的执行，不覆盖用户自行暂停或改动的 Goal。

自动执行仅在用户对本次任务明确委托时启用。授权绑定租户、会话、原始输入、授权范围、有效期及实际使用的计划版本，支持撤销和幂等消费。UI 与收据明确标注“用户确认”或“用户授权自动执行”。模型自述已批准、普通文档文字及仅开启 Goal 模式均不能授予批准权限。

用户本次授权在新会话持续开发及租户验证，无需重复询问同一工程工作权限。但验证人工确认链路时，必须实际操作并核验该链路；自动重跑收据不能冒充用户亲自确认。若由验收工具模拟认证用户操作，须标注为验收操作。需要真实用户决定的具体业务大纲及模型，展示可审阅版本后等待其决定。

### R7 使工艺预检问题能够一次定位和修复

保留 MD 单源构建方向；工艺说明、模板和检查器对章节角色、总结、来源及附录的定义必须一致。预检失败返回受影响的文件、章节或锚点、具体规则和期望结构，优先一次报告全部可确定问题。

最新作者日志表明其在排查总结章节识别要求时遇到额度终止。这是待复现的问题线索，尚不能直接判定检查器有误。下一会话应复现后区分说明不清、模板不一致、报告错误和检查器缺陷，并做通用修复；不得通过把最终业务答案写入提示词、修改旧样本或删除质量规则来通过。

## 五 开发和真实租户验证流程

1. 新会话读取本文、R12 CONTINUE 最新段落、项目 AGENTS.md 与对应 canonical 环境笔记；检查是否已有 Goal，有则继续，无则按用户明确授权建立 Goal。目标同时覆盖本需求和原 R12 最终业务验收。
2. 核实当前真实 Host、样本和后台观察进程。会话观察超时不等于业务停止；以原生状态和终止日志判断。已启动输入不得重发，已有推广和 reload 不得盲目重放。
3. 在现有工程之外创建隔离候选，保存并核验可恢复的纯净备份。工作树已有大量未提交改动，禁止 reset、清理或覆盖无关修改。按 R1—R7 分阶段实现并保存每项验收证据。
4. 完成对应单元/集成测试、构建、领域包一致性及实际隔离 Host 测试；涉及界面必须增加真实浏览器验收。隔离验证使用受控夹具，不消耗真实业务额度冒充测试。核验候选源码、runtime、域包与通过收据一致。
5. 推广前正式停止并封存待替换样本，核验全部所属会话停止，保存失败结论及产物摘要，保留原始收据和外部恢复记录。此前用户已授权停止旧样本后新建，不重复索取相同授权；若发现新的无关运行则先核实归属，不扩大停止范围。
6. 使用可回滚、逐文件冲突校验的推广方式；原子切换本地域包，受控重载 real，回读生效版本、模型、容量及维护策略。保持其他租户和历史冻结团队不受影响，临时维护设置须恢复。
7. 在 real 验证人工确认流程及批准前边界，再以全新会话、独立团队和目录验证原业务。自动重跑须记录独立的正式委托授权；只更换隔离标签，不添加观察者总结的业务答案或旧报告。原始输入只发送一次。
8. Goal 模式持续观察、收集事实和独立验收。失败则封存原因，在隔离候选修复通用问题，完成资格后再部署、全新复验。不得修改业务产物、给业务模型补答案或人工解卡后把样本标成自主完成。
9. 额度、认证或服务阻断应据实记录。没有授权购买额度、换付费方案或擅自换模型；可以继续不依赖该外部条件的工程工作。外部条件恢复后按正式新样本流程推进，不凭猜测重试旧业务。
10. 对照 A1—A10 和原 CONTINUE 逐项审计；任一证据缺失、过期或范围不足，Goal 保持未完成。达到完整目标才标记 complete，并交付需求落实表、部署/回滚收据、真实运行记录、最终报告及独立验收结论。
