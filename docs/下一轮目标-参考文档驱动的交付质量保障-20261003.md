# 下一轮工作目标：参考文档驱动的交付质量保障

日期：2026-10-03；2026-10-04 按用户后续三项原则更新。状态：实施中，业务质量目标尚未完成。部署与实跑的当前事实见 [架构与实施记录](领域包多工艺与AI选择-实施约束-20261003.md)。

前置依据：[上一轮复盘与参考附件诊断](插件优化第九轮复盘与参考文档接入诊断-20261003.md)。上一轮通信流程已经跑通，但最终报告有文字对比度、收益率计算基准和章节结构三项确定失败。下一轮必须解决这些质量问题，并补齐从工艺材料到最终交付的验证链；不能再次用“流程完成”代替“质量通过”。

**可直接采用的下一轮 Goal 表述：**

> 在保留已有工作并先备份相关插件代码、工艺技能和必要附件的前提下，将政策报告与成都合作报告两份参考源、工艺规则、组件、领域检查及审核要求闭环放入 `zhijian-realestate` 领域包，修复引用入口、路径、重复副本和规范冲突。一个领域包允许多个 skill，由 AI 根据任务选择 skill 或合法组合并记录理由；通用 Host 仅发现当前启用包、解析及冻结选择、按写作、渲染、审核角色交付所选工艺的必需材料，保存与任务及版本绑定的完整交付证据；建立绑定最终 MD/HTML/PDF 的结构、数字计算、视觉、PDF 和独立内容审核要求。全部适用的必需验收项通过后，插件才允许标记最终交付合格；缺材料、未执行、无法判定、证据过期和版本不一致均不得放行。修复上一轮三项确定缺陷，完成真实 Host 的失败拦截与恢复验证，再在 real 新建隔离 Session 重跑原车公庄任务，证明能够自动完成材料加载、生成、独立审核、有限修订和最终交付，无需观察者纠错解卡，同时保留并发限制、静默初始化、固定输入和事件驱动等待。完整记录适用范围、版本、质量证据、token、时长和残余限制，不以模型自报或局部脚本 ALL PASS 代替完整验收。

**“百分之百”落实为可执行约束，不承诺无法证明的模型能力。**

| 对象 | 下一轮必须做到 | 不能据此声称 |
|---|---|---|
| 必需材料覆盖 | 冻结清单中的每一项都存在、身份正确，并完整交付给指定角色；覆盖率 100% | 模型必然理解、记住并遵守所有内容 |
| 必需验收覆盖 | 冻结的全部适用必需项都有当前版本的有效证据；覆盖率 100% | 没有列入检查、无法观测的事实也必然正确 |
| 插件管理的放行 | 必需项失败、unknown、证据缺失或过期时，不能进入质量合格的最终交付状态 | 任意拥有宿主文件写权限的人或外部工具都无法旁路复制文件 |
| 最终版本一致性 | 审核、检查、集成与正式交付都指向同一组文件字节、材料版本和验收契约 | 旧版本通过可以自动认证新版本 |
| 人工与语义判断 | 逐项记录审阅范围、依据、计算或事实定位和未决问题 | 独立模型的判断获得数学意义上的零错误保证 |

参考文档能够固化规范、组件和反例，不能单独证明新报告中所有事实与推理正确。下一轮的工程保证是“约定的材料不漏交、约定的检查不漏做、未验证不冒充通过”，并以真实产物审计确认实际效果。三项已知缺陷必须修复，不能只完成这张表的机制建设就结项。

**一、先建立一个可追溯的工艺依据。**

1. 政策参考源为 https://bzf.meizu.life/credit-policy-v54-d38b.html；成都参考源为 https://yy.meizu.life/render/智见报告-成都数据集团合作/20260905-cddg-coop-report-v2-designer.html。保留本地完整原件、来源地址、获取记录、版本和 SHA；剥离统计脚本等非工艺内容时记录转换，不能把远程整文件和本地净化版本说成同一字节版本。
2. 所属领域包固定为 `zhijian-realestate`，不另建报告领域包，也不依赖包外全局工艺副本。保留两个技能职责：zhijian-report-craft 管结构、数据和验收规范；zhijian-designer-render 管渲染执行、组件映射及检查入口。所有附属资源从 SKILL 入口可达，路径按实际技能目录解析，不依赖成员当前工作目录，也不依赖旧 .openclaw 绝对路径或不存在的 shared 副本。
3. 权威原件在领域包内只维护一份，各 skill 共享包内资源；整个领域包可独立分发。确需构建副本时由构建过程生成并校验 SHA，安装、导出和打包均验证清单完整性。发现重复 id、路径解析歧义或副本漂移时明确报错，不能静默挑一份。
4. 区分“当前任务要求、适用工艺规则、视觉示例、历史业务内容”。从明确用户要求派生任务契约；契约不得降低用户要求。示例不能覆盖规范，更不能把历史数字、业务观点、页码缺陷或旧规则当成新报告事实。
5. 将两个示例明确为可选样式。AI 根据任务和技能适用说明，在生成前选择工艺组合及一个主样式，Host 不按领域关键词或角色硬编码代选；并记录借鉴另一示例的具体组件。统一处理固定 A4 与响应式网页、色板、封面封底页码等差异，避免混合互相矛盾的规则。
6. 提炼短的必读规范和真正可复用的 CSS/HTML 组件，包括文字色与装饰色的使用边界；把只有注释的图表目录补成可用组件或如实改名。全文参考件用于追溯与必要深读，不把两份约 220 KB 历史全文重复塞进每个角色的每一轮输入。

**二、把材料交付接入实际任务执行。**

| 角色 | 必需交付内容 | 接纳条件 |
|---|---|---|
| 主笔 | 当前写作规则、章节结构、数据纪律、缺失数据处理、适用验收矩阵 | 在开始相关正文任务前完成材料交付 |
| 渲染员 | 选定样式、规范组件、文字色规则、内容映射、屏幕与 PDF 要求、实际检查入口 | 在渲染前核验材料版本和 Markdown 输入版本 |
| 审核员 | 同版本工艺依据、逐项验收清单、可信检查结果、待审三件套固定版本 | 不得只收到路径或生产者自报 PASS |

Host 必须根据限定清单解析、读取并交付材料，记录任务、角色、会话、材料 id、版本、SHA、交付范围、完整性与接纳目标。文件路径可见或工具只返回 id/name/path，不能算正文已交付。若采用分块或提炼片段，清单必须明确哪些内容是必需输入，并证明全部必需内容都已交付；不能把未交付的完整 HTML 标记成已读。

材料缺失、哈希变化、交付超过预算或上下文截断时，必须给出可定位状态和恢复方式。不能静默截断后仍判准备完成。相同版本可缓存；新会话、新角色或材料版本变化必须重新建立对应交付证据。冷恢复或上下文压缩后保留短的必需规范与版本定位，不能仅凭旧会话的一条“已读”声明推断当前输入仍完整。

复用现有任务交接、持久状态和版本固定机制，但建立独立的技能参考类型：不得把技能正文伪装成原始用户消息，也不得把任意本地技能文件伪装成已审核上游业务产物。没有完成必需材料准备的任务，不能进入依赖这些材料的生成或审核阶段。

**三、把质量契约落实到真实检查和当前字节。**

在生成前冻结适用验收矩阵，逐项记录要求、范围、检查方式、证据来源和是否必需。状态至少区分 passed、failed、unverified、not_applicable。必需项只有 passed 才能放行；not_applicable 需要与交付范围相符的依据，不能事后用来消除失败。当前原任务要求 MD/HTML/PDF，不能因为通用模板包含 PPT 就擅自增加 PPT 硬要求。

| 验收领域 | 本轮必须解决的检查 | 不能接受的替代证明 |
|---|---|---|
| 参考材料 | 清单存在、路径解析、完整交付、版本绑定和副本一致 | 文件在 references 目录、模型说读过 |
| 章节结构 | 按真实章节及适用类型核验五件套的实质内容、开头与收束闭环、来源披露 | 只查 class 或关键词存在；通过重命名章节躲开缺项 |
| 数字与计算 | 关键数字来源与单位、计算式、参数、共同基准和结果重算；未知业务事实明确条件化 | 仅证明同一个错误被复制进 MD/HTML/PDF |
| 格式一致 | 从 Markdown 到 HTML/PDF 的内容与数字对应，选定锚点及适用全文核查范围明确 | 只检查文件存在或文件大小非零 |
| 视觉 | 实际浏览器 1280/375 布局、适用锚点和计算样式下的文字对比度；保留截图及检查证据 | grep 色值、CSS 源码看起来正确、样例曾经好看 |
| PDF | 真实 PDF 解析及必要渲染：封面封底、正文页码、品牌、章节大纲及正文可读性 | 在 HTML 中找到页脚代码，或统计 PDF 原始字节 |
| 独立审核 | 审核者与作者分离；逐项引用最终版本、依据、复算和未决问题 | 批量把所有 acceptance 布尔值写成 true |
| 最终交付 | 当前契约、材料版本、检查器版本、task/attempt 与最终三件套 SHA 绑定 | 旧截图、旧收据或修订前的审核结论 |

确定性检查由可信执行路径产生结果，不能接受生产者自行构造的通过收据。语义、事实适用性等尚不能可靠自动判定的项目保留独立审阅证据；无法判定时明确限制，不能伪造自动通过。外部数据未取得但原任务允许条件分析时，应核验该条件化要求和来源披露；不得为了通过门禁编造事实，也不能把允许保留的未知输入一概误判为任务失败。

上一轮的 F1、F2、F3 必须成为固定负例：低对比度文本、混用收益率基准、缺五件套的第五章应分别被对应机制识别，并给出可操作的修订意见。原始失败样本和当时契约保持不变。修复应使用通用的规则、实际渲染和计算依据，不能在检查器中硬编码车公庄报告的句子或这两个特定颜色。

规则覆盖必须在结果中明确。例如，限定数字锚点一致性不能命名为“全文数学正确”；局部 DOM 几何检查不能冒充完整视觉审美认证；现有来源、收束、PDF 三项检查不能冒充全部 G1–G5。调整规则需要记录原因与覆盖变化，并验证旧失败及正常样本，不能为取得绿色结果静默删除失败项。

**四、完成状态与合格交付必须分开控制。**

生成产物可以保存为草稿；只有本次最终版本的全部适用必需项通过，插件才允许集成并标记质量合格的最终交付。若任务生命周期已经结束而质量仍失败，应显示“质量未通过/待修复”，不能让队长或 Goal 提前报告完整交付成功。

盘点实际交付和发布入口，覆盖插件管理的 review、integrate、交付复制与发布路径。检查与放行之间需要版本校验，不能在验收后替换字节再交付。任何成品修改均使对应旧验收失效；重新审核必须覆盖新版本全部适用必需项，可复用的证据也须验证输入和适用范围仍然一致。

对不受插件管理的直接 shell 复制、外部发布入口或拥有任意写权限的操作，必须清楚标注边界。它们生成的文件不能自动获得“已验收”身份。如果实施目标扩大为所有公开发布渠道均不可绕过，就必须同步纳管或限制那些实际发布权限；未完成前不得声称全系统不存在旁路。

沿用明确、有限的修复预算，跨撤回、重开、修订和重试累计保留。失败结果必须可定位；修复耗尽、外部终止性故障或必要检查无法执行时，持久记录阻塞、剩余工作和恢复入口，不自动空转。正常独立审核提出 findings 并触发修订属于预期工作流；观察者不得通过给答案、改任务状态或手工代修产物制造实跑成功。

**五、实施和验证按依赖顺序推进。**

1. **建立基线与备份。** 先保存相关插件源代码、构建测试文件、将要修改的技能与附件，生成清单和校验值；这些技能附件是本次直接工作对象，不混入业务数据、整库历史或其他无关内容。保留第九轮证据和失败产物，不覆盖原 Session。
2. **接通材料链。** 修正入口与路径，统一资源身份和副本生成；实现角色材料交付、接纳证据、版本变化和恢复处理。验证发现层与解析层取得同一资源。
3. **补齐验收链。** 修复无 section 也通过、把源码行数当图表数量、局部 ALL PASS 被扩大解释等缺口；实现结构、计算、真实视觉与版本绑定的适用检查，并接入有限修订流程。
4. **先做有界失败验证。** 离线与真实 Host 分别验证缺文件、错误版本、材料未交付、截断、重复接纳、缺检查依赖、伪造或过期证据、改动已审文件、空结构、原三项缺陷、修订预算耗尽和冷恢复。正常样本不能因页面元数据、合法条件分支或不适用交付格式被误挡。
5. **完成新 Session 原业务复跑。** 在 real 使用新 Session、新团队和新输出目录；保留原业务问题和已确定的模型、并发等控制条件。自动交付新工艺材料是本次被测机制；不得把缺陷正确答案写入业务提示，或把旧实跑产物给业务成员当新答案。记录版本和所有实际干预。
6. **独立验收并封存。** 复核正式运行完成状态、最终三件套、各项门禁、独立审核和实际交付副本。若复核发现新的必需项失败，结论继续为未通过，定位机制并有界修复；不能再次仅按通信闭环完成就关闭本质量 Goal。修复耗尽也只说明本次验证失败或阻塞，不代表目标已完成。

第一次完整新会话成功后，只因新失败、代码变化或尚未验证的关键恢复路径再增加实跑；没有明确验证问题时，不反复启动长业务以碰运气。不得在等待期间增加轮询模型调用。

**六、完成标准必须同时满足。**

- [ ] 工艺、参考件、组件、检查和审核要求均可从 `zhijian-realestate` 包内取得；移除全局工艺副本仍可使用。实际会话记录 AI 的 skill 选择及理由，且与启用包版本、材料和验收契约一致。
- [ ] 两份参考源有权威版本和用途说明，所有所需副本、组件及脚本可由技能入口和实际运行环境正确解析。
- [ ] 每个相关执行角色的必需材料交付覆盖率为 100%；不存在以目录可见、自报阅读或静默截断冒充完整交付的情况。
- [ ] 适用必需验收项的有效证据覆盖率为 100%；失败、unverified、缺依赖、缺证据和版本不一致的情形均在管理边界内被拦截。
- [ ] 第九轮三项负例按原契约被识别；修复后通过对应检查。最终新报告的计算口径、实质章节结构和实际视觉也经独立复核。
- [ ] 最终 MD/HTML/PDF 的当前审核、机器检查、独立审阅和交付副本绑定同一组字节。发布后替换、旧回执套新文件等关键错误有失败验证证据。
- [ ] 新 Session 实跑完成原业务、独立审核、必要修订与最终合格交付，观察者没有提示答案、代改状态或人工解卡；单元测试或单任务成功不能替代此条件。
- [ ] 原有并发上限、无额外子代理、静默初始化、等待唤醒、固定上游版本、修订预算、精确重放和冷恢复保障没有退化。
- [ ] 报告所有确定质量失败和必需未验证项均已关闭；不适用项和无法扩展的保证边界明确披露，不将它们包装为已证明的全局正确性。
- [ ] 用量按未缓存输入、缓存读取、输出和模型步骤分项保存，实跑与优化线程分开；耗时、失败、重试、人工干预、采样缺口及外部服务限制有证据。没有可比证据就不宣称节费。

**下一轮应交付六类结果。**

| 交付物 | 验收用途 |
|---|---|
| 相关代码、技能和附件的备份与清单 | 可追溯、可回滚 |
| 版本化工艺材料包、角色清单与可用组件 | 每次任务可获得明确、适用的依据 |
| Host 材料交付、版本绑定与质量放行实现 | 将材料和验收真正接入工作流 |
| 失败与恢复验证证据 | 证明未读材料、错误产物和失效收据不能冒充通过 |
| 新会话最终 MD/HTML/PDF 与独立审核 | 证明实际任务成功，不只证明框架存在 |
| 运行、token、时长和残余限制报告 | 可据事实判断质量与效率，不以承诺代替测量 |

本文件的核心约束是：参考文档负责给出依据，执行机制负责把依据交到正确角色，验收负责判断当前成品。任何一层缺证据，都不能跳过后宣布“百分之百保证交付质量”。
