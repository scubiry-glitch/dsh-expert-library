## 两次问题的共同机制与修复

较可信的机制是：任务不能顺利验收，导致多轮通信、重派和修订；每一轮又带入长上下文，累计缓存读取迅速增加。账本能证明大规模重复输入，不能精确分摊每项插件缺陷各浪费多少费用。

| 已核实的插件问题 | 实施的约束 |
|---|---|
| `in_progress + idle` 把等待审核当成掉线 | 持久化 `awaiting_review` / `blocked_external`，重启后仍不重派；由审核事件或队长显式恢复 |
| 状态工具只展示部分消息，却确认全部未读 | 按先入先出展示并仅确认本次返回的完整消息；其余保留 |
| 队长离线时消息没有可靠自动恢复 | 邮箱租约、代次准入、投递标记去重；异常释放租约，接受后确认 |
| 首次派单失败可能增加代次，没有后续状态事件又可能一直等待 | 投递有超时，同一代次按冷却自动重试；持续失败明确阻断；重启重建恢复计时，停止插件时取消计时 |
| 成员收到消息但邮箱确认丢失，恢复时可能再唤醒一次 | 直接投递和恢复投递共用持久消息 ID 回执，检查已排队及已消费消息；按 ID 过滤批次 |
| 同一 chat 重试可能反复产生副作用 | 接受幂等键，相同内容不重复计轮次或唤醒；键与内容冲突时报错 |
| 重派改变 task attempt，却留下旧 QualityRun | 同步迁移审核代次与负责人，归档旧 run；修订预算不静默重置 |
| 已通过或已集成的未完成任务没有修订出口 | 显式 `quality_reopen` 开新审核版本，保留历史与预算 |
| 摘要变化误阻断，实际文件变化反而可能漏检 | 审核、集成、完成三处复验真实字节；有真实文件证据时摘要只作说明 |
| 成员与审核者共写同一个交付路径 | Host 发布独立版本；下游按 artifact ID 固定输入，派单前校验 SHA256 |
| 发布的文件可能漏出默认审核合同 | 稳定的逻辑审核 ID 关联当前 attempt 最新发布版本，自动纳入审核；修订代次必须重新发布 |
| 验收后还要唤醒成员补做“完成”记账 | `quality_integrate(complete_task=true)` 同一次团队提交完成验收与收尾，并解锁下游 |
| 硬失败耗尽修复预算后可能放行 | 保持阻断并要求明确处理；预算用尽不能当成质量通过 |

成员提示词同时要求：只处理所属任务，先在任务 project 暂存再发布版本，消息传结论和定位信息，输入按需分页读取；等待期间不重复提交完成、不自我审核、不共写上游文件。Goal 的进展以持久任务与验收状态为准。

实跑发现了先前合成参与者测试没有覆盖的缺口：

1. 7 名成员的实际请求只有 8 个团队工具与 `subagent`，没有 bash/read/write；它们转而创建普通子代理，反复侦查环境。初跑约 676 万 token 来自这些后代，不能只统计队长和团队清单中的成员。
2. 成员在任务依赖未满足时，就由欢迎消息启动，产生错误领取和误用 `read_artifact` 等调用。
3. 普通子代理获得更宽的工具与委派能力，成员配置的工具边界和委派深度未完整传递到后代。
4. 模型请求在成功投递之后因余额不足结束；已有投递重试修复未把这类执行失败完整转为可见、持久的外部阻塞状态。
5. 队长仍通过 `sleep 120` 后直接读取邮箱文件等待审核，延迟处理新消息。该处并非邮箱丢失，而是等待策略和失败传播不足。
6. `quality_review.findings[].severity` 在工具参数中只声明为字符串，未公开实际合法值 `info/soft/hard`。独立审核者连续尝试 major、blocker、error、high 等值而失败，又派生子代理全盘搜索源码。准确说明虽然已送达成员 inbox，却被排到长调用之后的下一轮，不能把“已接受投递”当成“模型已消费消息”。
7. 当前证据校验一律拒绝 `acceptance_results[].passed=false`，包括 `needs_revision` 的非通过审核。这会使真正未满足条件的审核无法落盘为 blocked。后续修复应区分证据完整性与验收结果，仍严格禁止失败证据通过集成；不能用伪造 true 绕过。在本次 t1 的实际合同中，`output-present` 只检查产物存在且可审，实质缺陷另以 hard/soft findings 表达，之后已成功记录 needs_revision。
