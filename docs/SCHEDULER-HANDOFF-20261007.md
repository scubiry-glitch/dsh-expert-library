# 调度交接修复 · 2026-10-07

## 问题与证据

旧路径在 `kickMember` 开头要求成员 idle，导致运行中连信箱消息也无法投递。T17 集成后，队长已发出 T18 指令，但成员信箱未见投递/读取回执，T18 仍为 pending。另一个问题是旧 `acknowledgeMailbox` 在 Host 接收队列时便同时写 delivered/read/consumed，混淆了接收与消费。

## 核心改动（旧 DAG 不迁移）

- 将通知投递与新任务派发分离。现有运行/排队轮次可接收通知；冷启动与新任务仍受成员阻塞、父会话权限和并发限额约束。
- 0.1.5 Host 使用受父会话授权的 `deliverPrompt(..., 'steer')`，在下一安全步骤收取通知；旧 Host 兼容路径仍为 FIFO followup，不冒称支持步间消费。新任务始终走 queue。
- 成员信箱由 Host 队列接受后只记 deliveredAt；实际 `user/message` 事件或正式 status 收取才记 readAt/consumedAt。重启时通过子会话自己的消息收据补记消费，避免重复投递。
- 根据已提交的任务图重建 handoff 意图，持久化 since/phase/reason/noticeKey。上游完成即使未成功通知，后续调度或启动恢复仍能重建。
- 就绪任务自动生成一次带目标状态的提醒；每 30 秒进行状态协调，超过 120 秒未开始则向原队长发一次持久化告警。观察不取消工具、不代审、不重置 attempt。已完成任务的迟到提醒被拒收。
- 满并发时允许通知现有执行中的成员，不启动第二个空闲成员。手动暂停、用户门、评审门、runtime block 和移除成员仍被保留。
- 定时观察不绕过单条消息的自动投递重试上限；原始失败内容保留。重启后仍需按原权限确认不明执行结果，不盲目重放可能已有外部副作用的工具。
- 队长延迟恢复的 running 状态事件和 idle 会话启动事件都会重新扫描工作区，无需下一条用户消息。
- 超时告警先检查持久化幂等回执，避免经过时间/原因变化后重用相同键却内容不同，导致后续协调中断。
- 活动页面与团队 API 展示等待开始的时长和原因，区分成员忙、输入排队、恢复等待、容量不足、队长未连接等情况。

12. 队长延迟以 idle 状态恢复、没有任何状态变化或用户消息时，由 agent/session-start 自动恢复工作区协调。

## 边界

本修复关闭“成员忙导致通知不投递”和“就绪任务失去后续调度/告警”两条路径。它不会仅凭 running 时间自动杀掉进程；实际工具是否可重试、未知外部副作用、额度或身份错误仍要按原恢复门处理。真实视觉审美与实印验收不属于调度修复成果。
