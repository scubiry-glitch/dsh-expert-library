## 工具一：领域包优化建议

入口：`node scripts/qa/pack-improvement-advisor.mjs --pack <解压后的包目录> --evidence docs/analysis/account-c-pack-evidence-20261102.json --out <结果.json>`。

网页入口：从会话左侧「账号与设置」进入「能力管理 → 领域包」。版本中心安装的包在「已安装版本」展开当前启用版本，点击「优化检查」；本地包在「当前实例的领域包」点击同名按钮。检查结果显示在已安装版本下方。网页仅向当前账号管理员开放，通过账号绑定的 DSH 实例读取已启用包，只展示包内相对位置、问题依据、修复动作与开发文档章节；分享链接不能调用该接口。网页检查和下述 10 次 benchmark 分开，前者不创建会话、不运行任务，也不代表真实交付稳定性。该入口的源码已接入门户与 DSH 网关，需两侧发布后才会在生产网页出现。

按[合作伙伴开发文档](https://packs.meizu.life/guides/partner-devdoc)的实体边界读取 `pack.json`、场景 DAG、专家、输出模板、质量策略和数据提供方。先复用项目 v2 加载器做形态及交叉引用校验，再输出 P0/P1 建议。每条建议都含包内位置、证据、修复动作和开发文档章节；本仓库样本索引使用匿名编号；工具会原样输出传入的会话 ID，因此真实执行证据和对应输出须在仓库外私有保存，不输出客户原话。工具只读，不修改包、不代替正式审核。

建议围绕六类问题：

1. 数据漂移：来源、口径、时间窗、城市、单位、freshness、缺口三态，以及跨期样本复算。
2. 门禁稳定：数据、结构、语义、格式的硬门禁、真实执行回执、误放行和两轮修复终态。
3. 模板格式稳定：`media` 与真实交付格式一致，固定章节、表题图题、表格合并、页边距和下载验收。
4. 专家拟人化：语气、方法、证据标准与否决项；用盲评样本识别套话和无证据推断。
5. 任务节点稳定：DAG 输入输出、依赖、超时、重试与中断恢复。
6. 发布交付：审核、发布、安装、可调用、下载的版本号和哈希一致。

对账号 C **已打包的**城市月报 `prod.city-house-price` v2.5.1 ZIP 解压后试跑（ZIP SHA-256：`597ddb499d3358b8fb5e64cc2ac2241bd6f9a15b91388499a119528b85469b39`）：Schema 通过；工具指出输出模板 `media` 只有 `markdown`，而包描述承诺 Word 报告；无 `knowledge-providers/` 清单；格式和语义阶段无硬门禁（格式门禁现为 soft）。这些是进一步核验的建议，不能仅凭静态检查断言报告必然失败。工作区另一份同版本解压目录另有一处 gate `phase=render` 不在当前枚举内；该问题**不在已打包 ZIP**，故不混入已发布包结论。

## 工具二：10 次 benchmark

入口：`node scripts/qa/pack-benchmark.mjs --config <用例与执行器配置.json> --out <全新结果目录>`。固定 **10 次**，每次使用独立 session ID，同一包版本、同一输入、同一模型配置和冻结的数据快照。执行器通过 CLI/API 创建会话、发送任务、等待终态，并把实际成果文件和门禁回执写入本次 `receipt`。测评工具逐次核对会话 ID 不重复、成果文件真实存在且非空、所有必需硬门禁有回执且通过，再计分和聚合。执行器返回的质量数据仍需由独立验收脚本产生，不能由被测 Agent 自评充当证据。

配置合同为 `{"runs":10,"case":{"id":"...","prompt":"...","requiredArtifacts":["docx"],"requiredGates":["data","format"]},"runner":{"command":"node","args":["live-adapter.mjs","{caseFile}","{receipt}","{runId}"]}}`。执行器必须写 JSON 收据，包含 `mode=live`、唯一 `sessionId`、`status`、`startedAt`/`endedAt`、`artifacts[{kind,path}]`、`gates[{id,hard,pass,evidencePath}]`、`repairRounds`、`dataChecks{verifiedClaims,totalClaims,driftCount}`、`formatChecks{passed,total}`、`taskChecks{completed,total}`、`expertRubric{score}`。真实用例的配置与执行器应保存包版本、模型与数据快照哈希；每项 gate 的 `evidencePath` 指向非空机器回执文件。

| 维度 | 分值 | 可核验输入 |
|---|---:|---|
| 完成与交付 | 25 | 终态 completed；必需文件存在、非空、SHA-256 入报告 |
| 数据与证据 | 20 | 逐项已验证数字 / 全部数字；漂移数必须为 0 |
| 硬门禁与修复 | 20 | 必需 gate 全通过且有本次回执；修复最多 2 轮 |
| 模板与渲染 | 15 | 必备章节、表图、版式检查通过率 |
| 任务节点 | 10 | 必需节点完成率；单次失败归因到节点 |
| 专家表现 | 10 | 独立 rubric 的证据锚、判断和表达评分 |

输出包括逐次失败码、分数、会话 ID、成果哈希、门禁结果及耗时，并汇总通过次数、平均分、p50/p95。**稳定放行口径：10/10 个真实独立会话均完成、硬门禁全过、交付物有效，修复轮次均为 0 至 2 的整数，且每次至少 85 分。**工具不会把 fixture 或混合运行标记为真实稳定性。固定输入测的是重复稳定性；还需用换城、缺数、数据更新和中断恢复等扰动用例分别各跑 10 次，才能评价泛化与故障恢复。

当前核实：`node --test test/pack-benchmark.test.mjs` 已让计分器完成 10 次隔离 fixture 运行，10/10 收据通过、平均 100 分，同时正确标记 `non-live-or-mixed` 且 `stableForRelease=false`。这是**工具自检，不是账号 C 领域包的真实 benchmark 分数**。要得到真实分数，执行器必须接入账号 C 的会话创建和消息 API、持久化包版本与数据快照，并由独立脚本生成各项门禁回执。由于本轮没有固定的业务用例与可比较的数据快照，不能拿不同历史会话冒充同一用例的 10 次重跑。
