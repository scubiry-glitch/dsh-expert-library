租户接入配置向导

六步走完，让本租户安全地安装、启用领域包。全程只有第 1 步和第 5 步的备选批量路径需要宿主 CLI，其余都在 Web 界面上完成。

本向导涉及三个角色： 🏢 中心平台管理员 🧑‍💼 租户管理员（你） 🖥️ 宿主操作者 🏢 在 packs.meizu.life 操作（签发绑定码、可见性授权）；🧑‍💼 代表租户做审批与授权决定；🖥️ 管理租户那台 DSH 服务器的人（改配置、重启服务）——小团队里 🧑‍💼 和 🖥️ 常是同一人，但操作位置不同：一个在中心网站，一个在租户自己的 DSH Web 界面。
1开通租户 🖥️ 宿主操作者 · 一次性

这是唯一必须动宿主命令行的一步（租户根目录、成员映射是宿主级操作，Web 界面没有暴露）。把下面两条交给管理 DSH 服务器的人执行：

# 创建租户（生成租户 work 根 $DSH_HOME/tenants/<tid>/work/）
dsh-tenant tenant add --id acme --name "ACME 咨询"

# 把你的账号映射进租户并授予 admin 角色
dsh-tenant member add --tenant acme --user alice --role admin
执行完这步，之后所有审批、授权、安装都在 Web 界面完成。隔离由沙箱 workspace-write 硬约束兜底，不靠自觉。
2成员与设备审批 🧑‍💼 租户管理员 · Web 界面
  1. 成员用既有账号正常登录主站（yy.meizu.life）。
  2. 新设备首次登录会进入「待审批」状态，成员自己会看到等待页。
  3. 你在设备管理里放行或拦截（宿主 Web 设置页的租户管理区，或让 🖥️ 执行）：
🖥️ 命令行方式（可选）
dsh-tenant device list    --tenant acme
dsh-tenant device approve --tenant acme --device <deviceId>
dsh-tenant device block   --tenant acme --device <deviceId>  # 拦截即杀死该设备全部会话
租户策略 devicePolicy: strict 时，未审批设备一律拒绝；bind 时新设备待审批后放行。
3租户策略基线 🧑‍💼 租户管理员 · 核对即可

默认策略已经安全（workspace-write 沙箱），你只需要核对三项，通常不用改：

策略项默认值什么时候改
permissionPresetworkspace-write（写仅限租户 work 根）保持默认；danger-full-access 只应给 admin 角色成员
pluginAllowlist / rpcAllow/Deny租户可见插件面需要收紧可用插件集合时
ipAllow（CIDR）不限要锁定办公网出口时
🖥️ 命令行方式（可选）
dsh-tenant policy set --tenant acme --permission-preset workspace-write
dsh-tenant audit tail --tenant acme   # 越权尝试、设备事件全在审计里
4创建部署点并签发绑定码 🏢 中心平台管理员 · packs.meizu.life

部署点（Deployment）= 租户那台运行中的 DSH 宿主在中心登记的身份。

  1. 🏢 登录 packs.meizu.life → 左侧「分发 · 租户 × 可见性」→ 部署点 → 新建，命名建议与租户 id 一致（如 acme-prod）。
  2. 进入部署点详情 → 签发一次性宿主绑定码（dpc_bind_…，带时效，明文只显示一次）。
  3. 🏢 把三样东西通过独立渠道（不要和绑定码走同一通道）交给 🖥️ 宿主操作者：
    • 一次性绑定码
    • 中心 ID（如 pack-center-prod）
    • 中心 Ed25519 公钥（PUBLIC KEY PEM，部署点详情页可见）
绑定码是一次性的、有时效；作废或泄露就撤销重签。凭据与绑定码明文中心侧不留存，只留元数据。
5宿主侧绑定连接 🖥️ 宿主操作者 · 租户的 DSH Web 界面

这一步全程在浏览器里点，不需要命令行。操作位置是租户自己的 DSH Web 界面（不是 packs.meizu.life）：

① 确认包中心入口已开启

🖥️ 检查宿主配置 profiles/web/cordis.patch.yml 里有：

packCenterOrigin: "https://packs.meizu.life"

改过配置需重启 dsh web。之后打开 DSH Web → 设置 → 专家库 → 「包中心」卡片，四页签：领域包目录 / 已安装 / 更新 / 来源设置。未绑定时显示「尚未绑定中心；已有本地包不受影响」。

② 填绑定表单（三样东西来自第 4 步）

  1. 独立核对的中心 ID：填 pack-center-prod。「独立核对」的意思是：这个值必须来自第 4 步的独立渠道，而不是页面或下载内容里出现的值——防止中心身份被掉包。
  2. 一次性绑定码：粘贴 dpc_bind_…。每个码只能用一次，失败即作废，回第 4 步重签。
  3. 可信公钥：逐条填「公钥 ID + PUBLIC KEY PEM」（必须以 -----BEGIN PUBLIC KEY----- 开头，私钥会被拒收）。系统从不自动信任中心返回的未知公钥——这是防中间人的关键设计。

③ 点击绑定，验证结果

  • 成功后卡片显示：绑定状态「已绑定」、中心 ID、组织、凭据到期时间（约 30 天）、绑定时间。
  • 本地落盘 pack-center/private/connection.json（含机器凭据与钉扎公钥，勿外传）。
  • 到「领域包目录」页签能看到授权范围内的包即通。

④ 日常维护（都在这个卡片里）

  • 凭据到期前：卡片上有「重新绑定 / 轮换机器凭据」入口，重走 ②（让 🏢 重签绑定码）；绑定后让 🏢 撤销旧凭据。
  • 安装 / 启用：目录页签选包 → 安装 → 启用；更新永远不会自动发生，都在「更新」页签手动决定。
  • 常见报错：CONNECTION_REVISION_CONFLICT = 绑定信息已变化，刷新后重新核对；绑定码无效/过期 = 回第 4 步重签。
  • 解绑：只移除本地机器凭据，已安装包与可信公钥保留；中心侧凭据需 🏢 在部署点详情另行撤销。
🖥️ 无人值守/批量部署才需要 CLI

批量部署多台宿主时可用脚本走相同的绑定接口（参数同表单：bindingCode / expectedCenterId / trustedSigningKeys）。单台部署用 Web 界面即可。

6可见性授权与验收 🏢 授权 🧑‍💼 验收
  1. 🏢 中心「分发」→ 可见性授权：为本组织选 全部已发布包 或 白名单（逐包列出），并圈定可见的部署点集合；新包分发走「分发审核」由独立审核员复核。
  2. 🧑‍💼 按下面清单验收：
  • 成员在审批过的设备上可登录，会话列表只含本租户内容
  • 写操作被沙箱限制在租户 work 根内（越界被拒且有审计）
  • 包中心卡片显示「已绑定」，凭据未过期，目录里能看到授权的包
  • 安装一个包并启用成功；更新页签不会自动变化
  • 越权/拒绝事件能在审计（dsh-tenant audit tail，🖥️ 执行）中看到
