0这份文档解决什么问题

智见专家 Agent 是一支由「专家库（Expert Library）」驱动的多智能体点评与研究团队。平台此前对合作伙伴的开放点主要是"提交数据、提交材料"；本文档把平台的原生扩展面完整开放出来：

你想做的事对应原生能力章节
把公司的专业方法论变成可被点名的"专家"Expert Profile（schemaVersion 2）§4
设计"并行研判 → 融合成文"的生产流水线Scenario 任务 DAG§3
沉淀写字/用数/渲染的工艺规范Skill（SKILL.md）§5
规定交付物长什么样、什么算"过关"输出模板 + 质量门禁§6
让专家用上你的数据（行情/指标/政策/房源）数据源通道 expert_provider_call§7
组织辩论 / 圆桌 / PPT / 研报协同形态协同模式§8
i

文中所有 平台现有机制 均已在生产专家库中落地并有实例可查；标注 合作伙伴新增物 的是伙伴侧交付物的建议规范，随领域包一并评审入库。

1平台总览

1.1 运行模型（30 秒版）

① 先归型clarify：话题类型 + 必答口径→ ② 路由route：框架 A-E + 候选专家→ ③ 用户拍板专家人选绝不代选→ ④ 建队apply：persona 烘焙 + DAG 播种→ ⑤ 并行研判专家独立作业→ ⑥ 融合合成主笔在主题下融合→ ⑦ 质量门禁硬门阻断 /「质 NN」→ ⑧ 匿名化渲染领域·首字母→ ⑨ 评分回写evaluations.jsonl
  • 队长-成员模型：队长拆解目标为任务 DAG；成员是持久子代理，各自满回合作业，队内邮箱直连通信。
  • attempt 能力机制：任务携带 attempt_id，重分配即吊销旧尝试——晚到的旧结果无法覆盖新归属。
  • persona 烘焙：成员不是通用助手，而是从 Expert Profile 生成的"人格+方法+约束"整体，并注入既往评分反馈的校准摘要。

1.3 领域包标准目录

伙伴交付物按此组织：

domain-packs/<pack>/ ├── pack.json # 包清单：id / version / schemaVersion / caliberDeclarations ├── experts/<id>.json # 专家 Profile（§4） ├── scenarios/<id>.json # 任务 DAG 场景（§3） ├── output-templates/ # 输出模板（§6） ├── quality-policies/ # 质量门禁（§6） ├── knowledge-providers/ # 知识供给声明 ├── routing/ # 路由表与框架投影 ├── method-packs/ # 方法包 ├── domain-knowledge/ # 领域知识 ├── team-templates/ # 团队模板 ├── generated/ # 构建产物（生成，不手写） └── source/ # 溯源：raw-profiles / SOURCE-MANIFEST.json / docs / library

pack.json 实例（节选自房产领域包）：

pack.json{
  "id": "zhijian-realestate",
  "version": "1.1.0",
  "schemaVersion": 2,
  "name": "智见点评·房地产领域包",
  "description": "33 位房地产领域专家基线（bk-002~bk-034，五大领域）……",
  "caliberDeclarations": {
    "克而瑞": "克而瑞/普睿监测口径",
    "中指": "中指院口径",
    "贝壳": "贝壳成出口径",
    "统计局": "国家统计局口径"
  }
}
!

口径声明（caliberDeclarations）是领域包的"数据宪法"：包内专家引用任何数据源时，必须能落到这里声明过的口径上。

1.4 核心实体总览：十类实体的含义与边界（树状图）

领域包目录里的每个子目录都是一类实体。按「流程 → 资源 → 资产 → 规范 → 工艺」五层理解；每类实体用"是什么 / 边界（不是什么）"两句话钉死。层与层之间靠显式引用衔接——边界即引用关系。

i

给你的交付载体：领域包 domain-packs——pack.json（id / version / schemaVersion / caliberDeclarations 口径声明）+ 各子目录，一个包 = 一个评审入库单位。接入先在会话级知识目录灰度试运行一单（端到端交付 + GATE 文件 + 匿名化样本），验收通过后入库（§9）。平台内部部署路径与预设机制不在合作伙伴视野内；打包结构请直接以样例包为基线（样例包下载页 ↗）。

  • 流程层 · 怎么走
    • 场景 Scenario一次生产的任务 DAG：任务节点 + 依赖 + 专家指派 + 交付物声明（scenarios/*.json）。
      只管「步骤怎么走」；自身不含方法内容，靠引用专家 / 技能 / 模板 / 门禁的 id 组装
    • 团队模板 Team Template固定成员阵容的快捷装配（team-templates/）。
      只管「派谁上场」，不管步骤顺序——与场景互补：场景管步骤，团队模板管阵容
  • 资源层 · 谁来做
    • 专家 Expert人格化作业单元 = persona + 方法 + 约束 + 输出规范，建队时烘焙成成员（experts/*.json）。
      只定「谁来做、怎么判断」；不定「做几步」（场景）与「交付长什么样」（输出模板）
  • 资产层 · 用什么做
    • 方法包 Method Pack结构化作业方法论：评审协议、测算规程，由专家 methods[] 引用（method-packs/）。
      是专家的「手艺」；不管行文与用数纪律（技能包），也不含数据本体
    • 领域知识 Domain Knowledge领域事实与参考资料：术语、制度、案例库（domain-knowledge/）。
      是「事实与资料」，不是「怎么做事」；经知识 Provider 挂到专家
    • 知识 Provider knowledge-providers/知识供给声明：什么知识、以什么 scope、供给谁（knowledgeBindings）。
      只是知识的「配电箱」——管供给关系，不生产内容
    • 工具 Provider expert_provider_call外部数据与受控操作通道（Wind / 政研通 zyt / 贝壳），带能力契约与审批（§7）。
      只管取数与受控操作；不进入人格，不决定行文
  • 规范层 · 长什么样 / 怎么过关
    • 输出模板 Output Template交付物的静态形态：章节骨架、字段、渲染要求（output-templates/）。
      管「长什么样」；不管过程怎么走（场景），不管过不过（质量策略）
    • 质量策略 Quality Policy验收规则：硬门阻断 / 软门警告 / 修复轮次，任务完成时自动运行（quality-policies/）。
      只做「过关判定」，不参与生成；与 outputSchema.rubrics（专家输出评分）互补
  • 工艺层 · 怎么做好
    • 技能包 Skill可复用的做事工艺：行文逻辑、数据纪律、门禁细则、渲染管线（skills/<id>/SKILL.md + references/）。
      横切层，被场景或任务点名引用；不替代专家人格，也不替代输出模板

装配关系：边界即引用边

引用边字段 / 机制含义

场景 → 技能包scenario.skill / 任务描述点名工艺注入

2快速开始：七条接入路径

先分清主线：你是给平台加资产（贡献型 A / B / C / F / G），还是用平台产能（消费型 D / E）？很多伙伴两者兼具——先用消费路径跑通价值，再走贡献路径沉淀资产。

路径 A · 数据集团【贡献型】

数据源伙伴

带来数据与口径，专家作业时经 expert_provider_call 取用。最小交付：① 能力契约表（capability id / 出入参 schema / 频率 / 口径 / 单位 / 时滞）② 测试端点 + 只读凭据 ③ 数据字典。先只读、后灰度；写操作走审批、失败关闭（§7）。

路径 B · 专业机构【贡献型】

评估公司 / 会所 / 律所

把执业方法论变成可被点名的专家。典型角色：评估公司 · 会所 · 律所 · 券商投研 / 银行（独特关切：研报合规门禁与免责规范）· 行业协会（执业准则 → 方法包、评级标准 → rubrics）· 高校 / 科研院所（学术 persona + 计量模型方法包）· 咨询公司（方法论框架包）。最小交付：① 1~5 位专家 Profile + 溯源材料（执业准则、署名文章、方法论白皮书）② 1 个场景 DAG（如"估价报告复核""审计意见点评"）③ 1 套输出模板 + 质量门禁（§3/4/6）。

路径 C · 内容模板【贡献型】

内容与模板伙伴

沉淀工艺与视觉规范供生态引用。最小交付：① Skill 包（SKILL.md + references/）② 渲染模板（视觉 register、封面封底范式、图表选型表）（§5/6）。

路径 D · 企业分析需求方【消费型】

企业内部的分析需求

战略 / 市场 / 投研部门把专家库当内部研报与决策支持生产线：自有专家与领域包专家混编建队；带来决策场景、私有口径（dataView: internal）与脱敏清单。交付为私有分发（内部分发，不走公网外链）；内部包默认不入公共领域包，反哺公共库需脱敏后走 B 路径评审（§3/7/10）。

路径 E · 媒体与出版【消费型】

报纸 / 杂志社

把点评 / 研报 / 圆桌 / 辩论生产线用于内容工业化（专栏点评、市场解读、专题研报）。带来栏目体例（把输出框架裁剪成刊物骨架）、刊物文风（风格 Skill）、署名与版权规范；拿走多形态生产线、多版本管理（发布 slug 稳定不覆盖历史）与发布合规。署名遵守匿名化红线——对外只列「领域·首字母」（§5/6/8/10）。

路径 F · 生态开发者【贡献型】

工具与集成开发者

不供数据、不当专家，为生态造工具：Skill 包、场景 DAG 模板、渲染模板与管线、数据连接器（必须走 A 的能力契约，§7.5）、自动化集成。拿走生态分发（技能经四层发现机制被所有团队引用）与质量信誉（门禁 + 评分反馈可追溯）；连接器只读优先、不绕过审批（§3/5/9）。

路径 G · 个人专家入驻【贡献型 · 轻】

独立顾问 / 学者 / KOL

以个人身份把方法论沉淀为专家数字化身——专家库的本源。带来：1 份个人 Expert Profile（persona + 方法 + 约束 + rubrics，§4）+ 知识底座（署名文章授权材料）。拿走：自己的专家被任意团队点名引用；评分反馈闭环让 persona 越用越准（§4.5）；对外匿名呈现保护隐私（只列「领域·首字母」）。授权是硬门槛：无授权来源不入库，观点必须可溯源；不供数据、不设数据通道。

七条路径共用同一个入库流程（§9）与治理红线（§10）；贡献型交付物一律按样例包结构组织（样例包下载页 ↗），个人专家（G）最小只需 Profile + 授权书。

3能力一：定义任务 DAG（Scenario）平台现有机制

3.1 文件与格式

  • 位置：domain-packs/<pack>/scenarios/<id>.json（入库）或 <knowledgeDir>/scenarios/<id>.json（会话级）。
  • 格式：JSON，schemaVersion: 2。
  • 语义：任务数组即 DAG；dependsOn 引用任务数组下标（0 起）；所有依赖完成后任务才可被认领。

3.2 字段表

字段类型说明
idstring场景唯一 id（如 valuation-review）
name / descriptionstring名称与描述（会展示给建队者）
version / schemaVersionstring / int版本；当前 schema 版本为 2
domainstring所属领域标识
intents[]string[]路由意图词（命中即候选该场景）
requiredCapabilities[]string[]需要专家具备的能力点
routingPolicy.candidateHints[]string[]候选专家提示
teamTemplate / outputTemplate / qualityPolicystring引用团队 / 输出模板 / 门禁策略的 id
knowledgePolicy.required[]string[]必须挂载的知识供给（如 local-knowledge）
toolPolicy.allowed[]string[]允许的工具面
experts[]string[]参与专家 id（快捷定义）
tasks[]TaskDagNode[]任务节点，见下表
deliverablestring最终交付物描述
skillobject场景级技能绑定 {id, purpose, appliesToTaskIndex}

TaskDagNode

字段说明
subject任务标题（完成时会烙上「质 NN」质量分）
description作业指令：写清输入、口径要求、输出形态；需要用 Skill 时在此点名"先完整阅读 knowledge/skills/<id>/SKILL.md"
expert承接专家 id
dependsOn[]依赖任务的数组下标

3.3 平台实例（research-report，节选）

scenarios/research-report.json{
  "id": "research-report",
  "schemaVersion": 2,
  "experts": ["researcher", "bk-004", "bk-007", "docs-coordinator"],
  "tasks": [
    { "subject": "资料与数据梳理",
      "description": "梳理资料与数据：关键事实、口径、时间线、争议点。",
      "expert": "researcher" },
    { "subject": "宏观研判", "dependsOn": [0],
      "description": "周期定位、政策路径、量化测算（数据带口径）。",
      "expert": "bk-004" },
    { "subject": "风险与债务视角", "dependsOn": [0],
      "description": "风险点、债务-通缩风险、关键监控指标。",
      "expert": "bk-007" },
    { "subject": "融合成文", "dependsOn": [1, 2],
      "description": "标题、摘要、正文、结论、风险提示、附录（数据与口径）。",
      "expert": "docs-coordinator" },
    { "subject": "渲染与分型验收", "dependsOn": [3],
      "description": "渲染前先完整阅读 knowledge/skills/finesse-ui/SKILL.md……",
      "expert": "docs-coordinator" }
  ],
  "deliverable": "完整研报（markdown）+ 渲染成品 + GATE 验收文件。",
  "skill": { "id": "finesse-ui", "appliesToTaskIndex": 4 }
}

要点：[0] → [1],[2] → [3] → [4] 构成"梳理先行、双视角并行、融合收口、渲染验收"的经典菱形结构。

3.5 运行时规则平台现有机制

  • 成员同一时刻只能持有一个未完成任务；空闲成员由调度器自动认领就绪任务（含后续轮次）。
  • 任务认领返回 attempt_id；成员更新任务必须携带当前 attempt——重分配后旧 attempt 立即失效。
  • 队长可随时改派 / 接管 / 重试（reassign）：旧尝试先吊销、旧成员先静止，避免结果互相覆盖。
  • 队长可对单个成员追问（澄清口径、修正延伸），不重建团队、不新建任务，回合计数可追溯。

6能力四：输出模板与质量门禁

6.1 输出模板（output-templates）

  • 位置：domain-packs/<pack>/output-templates/<scenario-id>.json。
  • 内容：交付物的章节骨架、字段要求、渲染要求（视觉 register、封面封底范式、图表选型）。
  • 生产参照：研报场景的"五件套"章节骨架 + 点睛图九类选型表沉淀于 zhijian-report-craft/references/report-template-fivepiece-v1.md，伙伴可直接以此为基线裁剪。

6.2 质量门禁（quality-policies）平台现有机制

  • 位置：domain-packs/<pack>/quality-policies/<id>.json；结构 {id, version, schemaVersion, gates[], maxRepairRounds}。
运行机制行为
硬门（hard gate）未过完成被阻断，返回门禁 id、原因与修正指引；成员修正输出后重试提交，标题烙「质 NN·硬门未过」
软门（soft gate）警告放行，以 gate_warnings 返回
通过按门禁结果推导 0-100 质量分，烙进任务标题（「质 NN」）
归档建议落盘 GATE 文件（哈希 + 抽样截图），随交付物一并归档

合作伙伴起步门禁（建议基线，五道）合作伙伴新增物

  1. 禁例 token 0 命中——委托方要求脱敏的量值、禁用表述逐 token 扫描；
  2. 数字逐 token 一致——正文所有数字与数据底座表逐一对照，改数只改底座一处；
  3. 渲染 0 溢出 + 对比度 AA——双视口检查；
  4. 排版审计 0 问题；
  5. PDF 章节大纲逐项对照输出模板。

6.3 rubrics 与门禁的分工

outputSchema.rubrics 定义"专家输出好不好"（交叉评分与反馈）；quality-policies.gates 定义"交付物能不能出门"（自动阻断）。两者配合：rubrics 评分低的输出在融合环节降权，gates 未过的交付物根本到不了客户手里。

7.4 失败三态与数据纪律

情形处置
① 调用报错如实标注"通道失败"，不掩盖
② 成功但无数值区分展示层 / 交付层，标注"待补"，不得编造
③ 部分指标空序列如实写"该城该指标未交付"（数据侧未交付，不是通道故障）

四级数据标注（每个非引用数字必须落到一级）：测算（模型算，给参数）/ 估算（量级推断）/ 研判推断（分析性判断）/ 待补（进观察清单）。

✕

铁律：编数字比不回答更严重。伙伴通道若出数不稳，宁可让专家标注"待补"，也不得催生"看起来合理"的数字。

9.4 v2 形态自检与自动适配（入库前必跑）

10治理与合规红线平台现有机制

  1. 先归型、再路由：口径未收集齐（用途受众 / 数据来源 / 城市 / 时段 / 脱敏 / 领域侧重），不建队、不开工。
  2. 用户拍板：专家人选永远由用户确认，系统不代选；同题对比建议"一乐观/底部派 + 一风险揭示派"的立场配对。
  3. 匿名化对外：只列「领域·首字母」；已故专家只可引用历史观点。
  4. 数字纪律：编数字比不回答更严重；四级标注 + 数据底座单点维护 + 量值脱敏走禁例 token 清单。
  5. 审批失败关闭：写/敏感操作无审批即拒绝，不降级、不绕行。
  6. 公开性自查：任何渲染产物发布为公网外链前，必须确认内容不涉密、可公开（外链免登录直出）。
  7. 授权溯源：专家 persona 观点、知识材料、数据引用全部可溯源；无授权来源不入库。

B附录 · FAQ

Q1：我们只能贡献数据，没有 AI 工程能力，可以接入吗？

可以。路径 A 只要求能力契约表 + 测试端点 + 数据字典；persona 化、能力注册、评审由平台侧完成。

Q2：我们的方法论是商业机密，怎么保护？

Expert Profile 的 internalName 与知识底座仅在会话内部使用；对外呈现只有「领域·首字母」。涉密材料可只入库摘要层，溯源材料分级存放。

Q3：我们的专家和房产域的 bk-0xx 会冲突吗？

不会。领域包自有 id 建议带包前缀（如 bk-val-001）；平台保留段为 bk-0xx 与内置角色名。

Q4：门禁会不会把正常交付卡死？

硬门只在"数字不一致 / 禁例命中 / 渲染溢出"类客观错误上阻断，且返回修正指引；主观质量走 rubrics 评分与软门警告。

Q5：能先小范围试用吗？

可以。灰度阶段一切交付物挂会话级 <knowledgeDir>/ 运行，验收通过后才入领域包，全程可回滚。
