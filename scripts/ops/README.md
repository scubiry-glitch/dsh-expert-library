# 领域包发布与线上激活

生产入口：`release-domain-pack.mjs`。运行环境为已部署发布中心与 DSH 的宿主机，Node 22、Git、Python 3/PyYAML、已构建的本仓库 `lib/`，以及生产 web profile 的 `yaml` 依赖。

## 一条命令

在本仓库运行（相对配置路径按当前目录解析）：

```bash
node scripts/ops/release-domain-pack.mjs scripts/ops/zhijian-realestate-1.6.0.json --apply --approve-reviewed
```

不带 `--apply` 只检查源码、远端版本标签和配置中的回归测试。`--approve-reviewed` 表示操作者已经获得发布授权并完成本次变更审核；它使用已有、不同于提交人的审核账号，保留发布中心审核记录，不代表另有一名人工独立审阅。

## 下次版本

1. 在领域包干净工作树内完成修改、生成产物和版本号更新，提交 Git。
2. 将该提交和 `v<版本号>` 标签推送到配置中的仓库。脚本校验标签指向固定 SHA，不会替你强推或覆盖已发布版本。
3. 复制本次 JSON 配置，更新 `version`、`sourceDir`、`sourceCommit`、`notes`、`reviewComment`；按此次变更选择 `verificationTests` 和 `requiredSkills`。
4. 执行上面的命令，换成新配置路径。

## 自动执行及验收

- 校验包 ID、版本、干净工作树、Git SHA 与远端标签；执行领域包检查和指定回归。
- 创建或复用同版本同 SHA 的提交，验证、送审、批准，等待发布中心正式签名发布。
- 使用生产 DSH 的管理队列完成安装与启用，执行完整包合并及研究工艺预检；不直接写 inventory，不伪造认证会话。
- 对安装成功但启用失败的版本，下一次运行通过正式 `enable` 事务恢复。
- 最后校验已激活的 release ID、版本、签名完整性、运行时快照及必需 Skill 文件。
- 脱敏回执写入 `receiptDir/<packId>-<version>.json`；退出码 0 且输出 `verified_active` 才表示完成。发布成功不等于激活成功。

相同命令可以重跑，成功版本不会重复发布，也不会重复启用。失败、超时、版本与 SHA 不一致均停止；修改原因后重跑。重新执行失败的启用事务仍经过正式校验，不强制绕过冲突。

## 生产加载范围

本次生产工作区包含领域包开发源码和 V5 测试副本；自动发现会使本地 `zhijian-realestate` 与发布中心版本冲突。配置的 `legacyEnabledPacks` 显式保留其他原有本地包，`zhijian-realestate` 由发布中心管理。开发和测试文件保持原位。

该字段仅控制工作区／旧版包，不控制发布中心激活列表。以后增加需要加载的本地包，应同步更新这份名单；不要把中心管理的同名包加入。配置更新仅修改 `expert-library.enabledPacks`，校验其他设置完全一致，保留权限为 0600 的备份，随后重启配置指定的 DSH 服务。配置未变化时不重启。重启中断可根据回执目录内的 marker 续跑。

`materializeAliases` 是显式列出的旧环境修复名单：仅将同一包目录内的本地软链接转换为内容校验一致的普通目录，以满足工艺的严格路径校验。原始隐藏目录和带时间戳的隐藏链接备份保留；禁止跟随目录外链接。已经是普通目录时不做任何修改。它不修改发布中心工件；新环境没有这些历史别名时可省略此字段。

`production-pack-host.mjs` 从真实生产设置和工作区注册表构建管理上下文；生产队列由单执行器锁串行处理。修改应用或新增运行时服务依赖后，需同步检查此适配器与线上初始化逻辑一致。

## 凭据与回退

配置只记录凭据目录和账户名；密码由已有的 `credentialDir/<subject>.pw` 读取，cookie 仅在内存中。禁止把密码、token、settings.yaml 内容复制进仓库或发布回执。

旧版本保持安装，可在原生产包管理界面使用正式回滚操作。不要直接编辑 `inventory/state.json`。本次释放签名版本为不可变工件，修复包内容需递增版本，不能覆盖 1.6.0。
