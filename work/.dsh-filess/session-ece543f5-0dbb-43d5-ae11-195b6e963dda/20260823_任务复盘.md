## 一、我做错的事（按严重度排序）

### 错误 1：expert_review_apply 传错专家 id 格式（低级错误）
- **现象**：第一次 apply 报「存在未知专家 id：BK-033, E08-08」——我按 route 返回的大写 `BK-033` 传参，实际 schema 要小写 `bk-033`。
- **根因**：没读 route 输出的字段约定就照抄；route 的 `id` 是内部小写 id，我却复述了展示格式。
- **代价**：浪费一次工具调用往返。

### 错误 2：beike-pack roster gate 修复只做了一半（核心错误）
- **现象**：apply 报 `required-capability-unsatisfied (beike.review)`。我修了 `zhijianMetaToExpertV2` 未注入 `beike.review` 的问题（加 `beikeExpertToV2` stamp），**但没验证 overlay merge 会覆盖它**——`zhijian-realestate` overlay 在发现顺序上排在 beike 之后，merge 后序覆盖先序，把 bk-033 覆盖回无 `beike.review` 版本，第二次 apply 仍失败。
- **根因**：只验证了单包构建（`buildBeikeDomainPack()`），没有用完整运行时链（`resolveRuntimePack` merge）模拟。**验证手段不全**是根因。
- **代价**：多修一轮；正确解法是场景 `requiredCapabilities` 改用所有专家必然认领的 `zhijian.review`，不依赖 overlay 顺序。

### 错误 3：t7 渲染节点指派给领域专家（违背职责分离）
- **现象**：t7 渲染与生成我指派给**杨现领（居住服务领域专家）**。
- **根因**：没意识到渲染是通用工艺活（finesse-ui/pptfast/video-shotcraft），该由内置通用专家（designer/docs-coordinator）承担——系统 ppt-gen 模板早有先例（t4 渲染默认 docs-coordinator）。
- **后果**：杨现领完成质量尚可（HTML/PDF/PPTX/视频全交付），但职责错位；用户随即指出「默认指派内置通用专家」——这是用户提醒我，不是我先想到的。

### 错误 4：t6 质量分被 gate 配置扣到 20，我最初判定「不影响内容」就放过了
- **现象**：t6 完成时报 `gate-artifact-missing @t2`（模板 gate 绑定逻辑 t2，fan-out 后物理任务重编号，gate 落在无 artifact 的中间任务上），硬门拦 2 轮后带 warning 放行、质 20。
- **根因**：模板 `frameworkTeamTemplate` 的 gates/deliverables 绑 t2，与 fan-out 物理 id 错位——这是插件 bug，且**我一直没修复它**，直到用户提出渲染节点设计时才顺带修（gate 改绑 t3）。
- **教训**：质量分 20 是明显异常信号，应该当时就定位修复，而不是「不影响内容」带过。修复动作拖了 1 个小时。

### 错误 5：build-zhijian-pack 漏生成 expert-memory 文件（导致专家研判缺知识库）
- **现象**：杨现领研判时反馈 `zhijian.expert-memory` 不可用（domain-packs/zhijian-realestate/ 无该文件）——文件直到 13:44 我跑 build-zhijian-pack 才生成，而研判 13:17 已完成。
- **根因**：我第一次重建 lib 时**只跑了 build-beike-pack，没跑 build-zhijian-pack**（当时以为 beike 修复只需重建 beike pack），导致 zhijian 领域包的知识文件缺失，专家记忆库不可用。
- **代价**：专家研判缺失内部知识库底座（幸好内置 Profile 兜底，内容质量未受大影响）。

### 错误 6：测试断言批量替换误伤 ad-hoc 测试
- **现象**：把 `task_id: 't2'` 批量 sed 成 `'t3'` 时，误伤了 3 个手工构造 t2 任务的 ad-hoc/no-policy 测试，导致额外 3 轮失败排查。
- **根因**：批量替换未区分上下文（gated 团队 vs ad-hoc 团队任务 id 不同）。

## 二、过程中的系统性问题（不全是我的错，但值得记录）

### 问题 A：调度器对终态任务的重复派发风暴
- t1/t2/t3 完成后，调度器持续对终态任务重复派发，成员反复 claim 被拒（本轮 5 位专家 + designer 都收到过重复派发通知）。这是插件 bug（昨天复盘也记录过）。

### 问题 B：gate 绑定与 fan-out 的架构缺陷
- `frameworkTeamTemplate` 的 gate/deliverable 用**逻辑任务 id**，但物理任务 fan-out 后重编号——运行时 rebind 逻辑（`physicalTaskIdsFor`）存在但绑错目标。已修（gate 绑 t3）。

### 问题 C：expert-memory 文件未随 pack 重建
- zhijian 领域包的 `domain-knowledge/` 是 build 脚本产物，漏跑即缺失。
